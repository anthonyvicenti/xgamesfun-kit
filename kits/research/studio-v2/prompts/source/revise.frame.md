## What you may edit

- `game/rules.js`: the game's own rules ([CONTRACT §3]({{KIT}}/CONTRACT.md)).
- `game/config/*.json`: tuning (`game.json` → `rules`, mechanic params, `look.json`, `world.json`, `characters.json`).
- Asset files **through their slots** (`game/assets.json`): replace the file a slot points at, or change its value. Read `assets.json` to find the slot; keep the same file kind (a `.glb` stays a `.glb`, a `.png` a `.png`) and the same path, so nothing else needs to change.
- `node {{KIT_TOOLS}}/create.mjs spec.json game` re-runs the kit's create on this game: it refreshes the vendored kit and `assets.json`, and **keeps** `rules.js` and `config/*.json`. Use it only if a mechanic or world you add needs a newer kit than the game has. Change `spec.json` first if you do.

## Slot edit or code edit

Choose the smallest edit that does what they asked.

| The creator asks for | Do |
|---|---|
| A menu, a pause screen, a health bar, a HUD meter or a wallet button | They are the kit's (§6g): change their words (`config/game.json` → `text`, e.g. `text.goal`), add a meter with `ctx.ui.meter`, or set the health mechanic's `label`/`color`. Never build your own or hide the kit's |
| a colour, size, speed, count, time, strength ("make the ball red", "bouncier", "shorter rounds") | A value in `config/*.json`: find the slot or the mechanic param in `assets.json` / `config/game.json` and change its value. No code. |
| "I keep getting knocked down", "the knockdown is too long" | A value: `config/game.json` → `fair` (`downSeconds`, `protectSeconds`, `botSkill`, `botsPerTarget`). |
| "I can't fire", "E does nothing" on an older game | `node {{KIT_TOOLS}}/upgrade.mjs game`, which keeps `rules.js` and the config values. |
| which parts of a player's look a loadout may set | A slot's `scope: "player"` comes from the kit; `config/game.json` → `loadout` (`slots`, `off`) changes which slots a loadout may set, and only when the creator asks. |
| one of their images or files in place of something visible ("use my image as the ground", "swap the ball for this") | Copy the file from `refs/` over the slot's file (same kind and path), or set the slot's value. A reference of role `direct` goes in as it is; `target` names the slot; `inspiration` is only a look to match. |
| one of their sound or music files ("use this as the shot sound", "play this song in the background") | Copy it from `refs/` to `game/assets/audio/<short-name>.<ext>` as it is (never re-encode) and run `node {{KIT_TOOLS}}/slots.mjs game --write` (it keeps the sound list; an mp3, ogg or wav also becomes a slot the creator can swap later), then point the sound at it in the game's one sound list, `game/assets.json` → `sounds` → `sounds` (the inner `sounds`, beside the other sound ids; never beside `version`, where the game never loads it): `"src": {"file": "assets/audio/<short-name>.<ext>"}`, keeping the sound's id and `bus`. For a sound the game doesn't have yet (background music, a new effect, several takes played at random), add an entry to that same list, e.g. `"sounds": {"version": 1, "sounds": {…, "zombie-death-1": {"label": "Zombie death 1", "src": {"file": "assets/audio/zombie-death-1.mp3"}}}}` (music: `"bus": "music"`, which loops), and play it from `rules.js` with `ctx.audio.play('<id>')` (music in `roundStart`). verify check 18 fails a sound outside that list, an uploaded file no sound plays, and an id the rules play that the list lacks. Add a line for the file to `game/ATTRIBUTION.md` (the creator's upload). If verify's audio check says it is too loud or too quiet, set the sound's `gainDb`. Never edit `game/audio/`. |
| a video they attached ("make it move like this", "this is the vibe") | It can't go in the game. The worker put still frames of it next to the file (`refs/<revision id>-frames/`): look at them and match what they show (the look, a motion, a layout) with values, slots or `rules.js`. |
| one of their 3D models ("use my model for the ball") | For a prop: copy the `.glb` from `refs/` over that `prop.*` slot's model file in `assets.json`, keeping the path; the kit fits it to the prop's size. A character body must be a rigged humanoid (the kit's `gf-humanoid-1`), so a plain model can't become a character: for "make the character look like my model" use it as a reference (the image row above) and say so. A model of role `inspiration` is only a look to match. |
| `request.json` → `slots` is not empty | The creator picked those slots in Studio's panel. Apply each one exactly (`value`, or the file named in `file`), then read the message for anything more. |
| "use my image as the character", "make them look like the picture" | A flat image cannot be a 3D body. Set `characters[].body` to `{"from":"reference","reference":"<revision id>","library":"<a fitting library body>"}` in `spec.json` and write it to `out/spec.json` (see "Generated models" above); **the worker** then turns the image into a body (with Meshy, only if the creator allowed it) and places it in the `character.body.<role>` slot after you finish. If that fails, the old body stays (and the delivery says so), so also tint it or set its nameplate so the change shows. Do not call Meshy yourself. |
| a new rule, mode, win or lose condition, new behaviour | `rules.js` (and the config it reads). |
| something the kit can't do (check `catalog.json`) | Do the closest thing, or write `out/failure.txt` (one or two sentences to the creator) if there is none. |

Keep what they didn't ask about as it is. Keep the spec's `notInV1` items out unless the creator asked for them now.
